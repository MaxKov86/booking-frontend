# Booking Frontend

Next.js (App Router) + TypeScript + Tailwind + TanStack Query + Zustand фронтенд для booking-системи. Працює у парі з окремим репозиторієм [`booking-backend`](../booking-backend) (Express + MongoDB).

## Запуск

Спочатку має бути запущений бекенд (за замовчуванням на `:4000`).

```bash
npm install
cp .env.example .env.local
npm run dev
```

Фронтенд стартує на `http://localhost:3000`.

Щоб перевірити: створи спеціаліста через бекенд (`POST /api/auth/register`), налаштуй йому розклад (`PUT /api/availability/:userId`), потім введи його `userId` на головній сторінці — і потрапиш на `/book/:userId`.

## Адмін-панель (крок 7)

### Автоматичне оновлення токена

`useAuthedRequest` — обгортка, яка підставляє access-токен і при `401`
**один раз** пробує оновити його через refresh-токен, після чого повторює
оригінальний запит. Це і є те, заради чого існує пара access+refresh:
access живе 15хв, без цього механізму користувача викидало б з адмінки
кожні 15 хвилин. Тут — прозоре продовження сесії до 7 днів.

Якщо refresh теж не спрацював (прострочений) — сесія чиститься, і помилка
піднімається вище.

**Спрощення:** при кількох одночасних `401` кожен запит ініціює свій refresh.
У продакшні тут була б черга (перший рефрешить, решта чекають) — для
адмін-панелі з одним користувачем це надлишкова складність.

### Захист від "блимання" логін-формою

`isHydrated` у `authStore` — до завершення відновлення з localStorage
сторінка не рендерить нічого. Без цього залогинений користувач на мить
бачив би форму входу (persist ще не встиг відпрацювати), що виглядає як баг.

### Токени в localStorage — відомий компроміс

httpOnly-cookie безпечніші (недоступні для JS, тому XSS не вкраде токен),
але вимагають CSRF-захисту й ускладнюють роботу фронтенду й бекенду на
різних доменах. Для портфоліо-демо localStorage прийнятний; у продакшні
з реальними даними варто перейти на cookie.

## Флоу бронювання (крок 6)

Чотири кроки в одному компоненті (`BookingFlow`): дата → час → форма → підтвердження.
Форма замінює вибір часу в тій самій колонці — так обрана дата лишається
видимою зліва як контекст, і користувач не гортає сторінку туди-сюди.

### Обробка race condition на клієнті

Поки користувач заповнює форму, інший клієнт може забронювати той самий слот.
Бекенд поверне `409` (unique-індекс у БД). Це має **окрему** обробку, а не
generic-повідомлення "щось пішло не так":

1. `ApiError` з `apiClient` несе HTTP-статус → форма розрізняє `409` від решти
2. При `409` користувач повертається до кроку вибору часу з поясненням,
   що саме сталось
3. `invalidateQueries` у `useCreateBooking` перезавантажує слоти — зайнятий
   час зникає зі списку автоматично

Без цього користувач бачив би незрозумілу помилку й не розумів, що треба
просто обрати інший час.

### Валідація

`validateBookingForm` — чиста функція, дублює правила бекенду навмисно:
клієнтська перевірка тут для UX (миттєвий фідбек), а не для безпеки —
бекенд однаково перевіряє все заново, бо клієнтську перевірку легко обійти.

## Архітектура

**Типи домену свідомо продубльовані** з бекенду (`features/booking/types.ts`), а не витягнуті зі спільного пакета — фронтенд і бекенд це два окремі репозиторії. Для проекту такого розміру shared-пакет додав би monorepo-тулінг, який ускладнює запуск і деплой більше, ніж економить на дублюванні кількох інтерфейсів.

**`apiClient.ts`** — обгортка над `fetch` з кастомним `ApiError`, який несе HTTP-статус. Це дозволяє компонентам розрізняти "мережа впала" від "409, бо слот щойно зайняли" — звичайний `Error` статусу не ніс би.

**TanStack Query** для всього серверного стану, **Zustand** — для клієнтського (з'явиться на кроці 7 для auth-стану адмінки). Той самий принцип розділення, що й у проекті 3.

## Палітра

Indigo/slate, світла тема за замовчуванням — свідомо інша, ніж у попередніх проектах портфоліо (amber/charcoal у 1-2, teal у 3). Публічна сторінка бронювання має виглядати нейтрально й довірливо для випадкового відвідувача, який лишає персональні дані.

## Структура

```
src/
  app/
    providers/       # QueryClientProvider (без MSW — реальний бекенд)
    book/[userId]/   # публічна сторінка бронювання
    page.tsx         # тимчасова стартова (ввід userId для розробки)
  features/
    booking/         # публічна частина: типи, api, DatePicker, SlotPicker,
                     # BookingFlow, BookingForm, BookingConfirmation
    auth/            # api, useAuthedRequest (auto-refresh), AuthForm
    admin/           # api, AvailabilityEditor, BookingsList
  shared/
    lib/apiClient.ts # fetch-обгортка + ApiError
  store/
    authStore.ts     # Zustand + persist (токени, юзер)
```
